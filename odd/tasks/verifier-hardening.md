# Feature: verifier-hardening

Follow-up to PD-06 of `production-delivery` (see `odd/tasks/production-delivery.md`). Opened 2026-09-19, after the fifth review-bot round on pull requests #24 to #27 and #29.

## Objective

Make the build verifier read built HTML exactly as a browser does, make it share the page's own link classifier, and close the coverage gaps the fifth bot round found, without ever letting editor content fail a build.

## Problem and why

`src/lib/built-html.ts` is a hand-written HTML reader. Five bot rounds (6, 9, 10, 7 and 9 findings) kept finding places where it differs from the HTML standard: raw-text elements, tag-name delimiters, comment endings, character references, and where `<head>` ends. Each fix added special cases, and the pull requests reached the 1000-line limit. The evidence says the tool is wrong, not the patches. `parse5` implements the standard's parsing algorithm, is what `jsdom` uses, and is already installed through Vitest, so declaring it costs a few lockfile lines and no download. It is a devDependency used only by the verification script: nothing reaches the site.

Separately, the verifier has its own copy of the conversion-link classifier and rejects analytics attributes on any link it does not recognize. Two copies that must agree are a standing risk that editor content fails a build.

## Scope

In scope: a parse5-based reader; migrating the four consumers to it and deleting the hand-written tokenizer; the verifier importing `analyticsEventForHref`; Instagram links that are equivalent to the configured one; the remaining fifth-round findings listed under VH-03.

Out of scope: any change to the site's markup or runtime code other than the shared classifier, new budgets, Lighthouse in CI, the deploy workflow (PD-07) and the launch checklist (PD-08).

## Constraints and decisions

- `parse5` is declared as a devDependency at the version already resolved (8.0.1). No other dependency.
- New reader API, in a NEW file so slice 1 cannot conflict with the open stack: `readLiveElements(html): LiveElement[]` with `name` (lowercase, as the parser read it), `attrs` (decoded by the parser, first duplicate wins), `source` (the start tag as written, for problem messages), `inHead` (the tree builder placed it inside `<head>`) and `text` (text content of `script`, `style` and `title`, empty otherwise). Live means: in the document tree, not inside `<template>` content; `<noscript>` content is text because scripting is enabled, as in a browser; comments are not elements; elements the parser created implicitly are skipped.
- One parse per page: the reader memoizes the last few inputs, because every check reads the same two pages.
- `hasRelToken`, `parseHeadersFile` and `getHeader` are not HTML parsing and stay where they are.
- Every behavior the old reader's tests pinned and that still matters must be re-expressed as a test of the new reader BEFORE the old tests are deleted: alt text with `>` or markup-looking text, comments, `<noscript>`, `<template>`, a script containing a closing-tag lookalike, attribute order, case and quoting, character references, duplicate attributes, raw-text elements, `<plaintext>`, tag-name delimiters. New for free from the parser: the `--!>` comment ending, a body opened implicitly, and metas only counting in `<head>`.
- The inline-content hashes for the policy check use `text` exactly as the parser yields it; verified against a real build.
- The page classifier and the verifier change TOGETHER. The agreement check (the page classifier's output fed to `checkAnalyticsMarkup`, hostile links included) becomes a real test.
- Pull requests under 1000 authored lines, planned up front as three slices; independent read-only review before opening; ready means CI green and the review bot's verdict in. If the bot keeps producing findings about markup Astro never emits, they are declined with that reason instead of patched.
- Base: slices are written on local branches from the tip of the open stack and transplanted onto `main` once #24 to #27 and #29 are merged. Nothing is pushed before that.
- TDD: off (no project or session configuration enables it; the user did not request it). Source: default. Runner: Vitest (`pnpm test`).

## Delivery strategy

1. `feat/html-reader-parse5`: VH-01. New reader and its tests, the devDependency. No consumer yet.
2. `feat/verifier-on-parse5`: VH-02, first half. The four consumers read through the new reader.
3. `feat/remove-handwritten-reader`: VH-02, second half. A pure deletion of the old reader and the tests that only pinned it. Split from the first half because together they were 966 lines, which would have left no room to answer a review, the mistake that blocked fixes on #24 to #27.
4. `feat/verifier-shared-classifier`: VH-03.

## Acceptance criteria

- The verifier's results on real builds are unchanged in both indexing modes, and every hostile input of the old reader's tests still gets the right answer.
- No hand-written HTML tokenizing remains in the repository.
- One function decides what a conversion link is, for the page and for the verifier.
- `pnpm check` passes without any secret or optional variable.

## Progress and evidence

- 2026-09-19 Opened. `parse5@8.0.1` confirmed installed through `jsdom` and `vitest` (`pnpm why parse5`); its `parse` takes `sourceCodeLocationInfo` and `scriptingEnabled` (default true), and implicitly created elements carry no source location. The user approved the devDependency.

- 2026-09-19 Pull requests #24 to #27 and #29 merged; `main` at 02ad8cd verified identical to the reviewed branches, CI green including the new `verify` job.
- 2026-09-19 VH-01 by a delegated writer. `src/lib/built-dom.ts` (123 lines) and 53 tests; `parse5` declared with a three-line lockfile change and no download. Writer's checks: `pnpm check` exit 0 with 27 files and 745 tests; six mutations, all caught, each confirmed applied. Parent readback and probes of its own choosing: every class the five bot rounds raised gets the right answer from the parser (the `--!>` comment ending, `<a@x>` and `<script@x>`, a body opened implicitly, a robots meta written in the body, raw-text elements, `&bsol;`, `&AMP;`, editor text posing as markup, `<noscript>` in head and in body). Native risk assessment `medium` (configuration change), so no separate verifier for this slice; the independent review covers it together with VH-02.
- Worth knowing about parse5 8.0.1: HTML tag names arrive already lowercased, so the lowercase call only matters for foreign content such as `foreignObject`; void elements DO carry a `startTag` location, whatever the package's own doc comment says, and the skip of implicit elements relies on that; `&#0;` and out-of-range numeric references become U+FFFD as the standard says, where the old reader left them as written; a `<template>`'s children live only in `.content`, and the explicit skip stays as a guard.

- 2026-09-19 VH-02 by a delegated writer, 28 call sites. Required tags (the robots meta, the policy meta, and the canonical and `og:url` of an indexable page) count only when the parser placed them in `<head>`; forbidden tags fail anywhere; a robots or policy meta outside `<head>` is a problem of its own. Verified on real builds in both indexing modes, and by tampering with a real build: the policy meta moved into the body, analytics attributes removed from a WhatsApp link, a cross-origin script hidden behind a `--!>` comment ending, one character changed inside the first executable inline script (the hash stops matching), and the robots meta moved into the body each fail the build with the right line. Six mutations by the writer and two by the parent, all caught. Sizes: 562, 412 and 554 authored lines.
- Two assumptions of the parent's brief were wrong and the writer reported them instead of working around them: the homepage's first inline script is the JSON-LD block, which is a data block and rightly has no hash (the hash probe was run on the first module script instead); and `&nvsim;`, used by an old test as an "unknown" reference, is a real one. That second finding exposed a stale rule, removed by the parent: a resource URL that still carried something like `&bogus;` counted as cross-origin because the OLD reader might have failed to decode it. The parser decodes every reference a browser decodes, so what remains is plain text and the URL is relative. The parent also folded the duplicated canonical and `og:url` lookups into one place.
- Deleted with the old reader, on purpose: tests of its API shape (a name filter, a predicate parameter, an identity pass-through) and one "attribute soup" expectation that was an artifact of its quote pairing, not what a browser builds. Every hostile input that still has a right answer is pinned in `built-dom.test.ts`.

- 2026-09-19 Independent read-only review of the three branches: no blockers. A differential probe of the old and the new reader over 35 hostile and ordinary snippets plus the four real built pages found only intended differences, two of them real bugs of the old reader (a `--!>` comment ending swallowed the rest of the page; an unquoted value with an apostrophe was cut in two). It confirmed on real builds in both modes that every required tag sits in `<head>`, and that no editor content can end the head early: the only raw HTML written there is the JSON-LD block, which escapes every `<`. Eight mutations: six caught, two absorbed, because two lines of the reader guarded what the parser already guarantees (the first of a repeated attribute, a template's children). Both lines removed by the parent; the tests that pin the parser's behavior stay. Also from the review: `built-html.ts` no longer described its content, so the `rel` helper moved into the reader and the rest is now `headers-file.ts`. The parent found the README still describing the old reader and fixed it. Known and accepted: the outer `<noscript>` and `<template>` tags are now visible to the checks (their content is not), which only matters if a template author puts an analytics attribute on one.

- 2026-09-19 Pull requests #30, #31 and #32 opened, CI green with one run each (the branches were pushed one at a time). Review bot: a thumbs-up on #31 and #32, and two rounds on #30 before "no major issues". Three fixes on the reader, each proven against the previous version: a qualified SVG attribute such as `xlink:href` keeps its prefix (it was filed under `href`, and the line the reviewer had called dead was masking the collision); the tree walk uses an explicit stack (recursion overflowed just under 10,000 levels; the parser itself is quadratic in depth, 1.5 s at 20,000 levels, so the test stops at 12,000); the attribute map has no prototype. One finding declined with the standard's wording: the text of `script`, `style` and `title` is the CHILD text content, which is what the policy check hashes.
- 2026-09-19 VH-03 by a delegated writer. `checkAnalyticsMarkup` calls `analyticsEventForHref` and the verifier's own copy is gone; the configured Instagram profile is recognized however it was copied (scheme, `www.`, case, trailing slash, a tracking query or fragment) by equality of the path, never a prefix; an agreement test feeds the page's decision for 35 links, hostile ones included, to the verifier. `/` and `/api/` are judged in every robots group by the rule a crawler applies (longest pattern, Allow wins a tie), which changed one old expectation that had pinned the bug: a group with `Allow: /` and `Disallow: /` leaves `/api/` open. XML comments no longer count in the sitemap. `src/lib/script-type.ts` is the one place that says what runs, shared by the inline-hash check and the eager JavaScript budget, which now counts classic external scripts. Total font bytes include the fonts of linked stylesheets. Verified on real builds in both modes; the budget table is unchanged, because the site has no classic script and no font in a linked stylesheet today. Tamper probes on a real build fail it with the right line: a Googlebot group with `Allow: /api/` beside `Disallow: /api/`; a 40 kB classic script (random content, since 40 kB of identical comment lines gzips to nothing, a flaw of the parent's brief); the sitemap's only `<url>` inside a comment.
- Parent changes on top of the writer's: the measuring had its own, weaker copy of the cross-origin test, so `src/lib/resource-url.ts` now serves the hygiene check and the measuring; a `data:` font or another origin's names no file and is skipped, a query or fragment is dropped, and a stylesheet that is not minified is read too (the writer's test had pinned a foreign font URL being returned as it was, which the script would then have tried to read as a local file); comments cut to the budget. The parent's first mutation pass had two mutations that were not real (one pattern never matched, one was split at the `||` inside the code); the assertion that a mutation was applied caught the first, and both were redone.

- 2026-09-19 Independent read-only review of VH-03: no blockers. It checked every link of both real built pages, in both modes, against the shared classifier (all match), round-tripped 20 hostile URLs through Astro's attribute escaping and the parser, and mutated nine lines. Fixed from it: a trailing NUL in the button's URL made the page and the verifier read two different links (the parser writes U+FFFD, `URL` drops it), only reachable by writing to the dataset through the API, never by typing, and now such a link is no conversion link for either side; the agreement test never left the attributes out, so a wrong Instagram URL in the verifier's first loop went unnoticed, now pinned; CSS names are read in any case (`URL(`, `@FONT-FACE`); a linked stylesheet with `@import` fails the measuring loudly instead of being undercounted, proven on a real build; the page's classifier and the checks share one URL normalization. Kept as it is, with reasons: `nomodule` is ignored because over-counting is the safe side; an absolute same-origin script URL is skipped by the measuring, but the hygiene check already fails the build on any absolute script URL, so nothing is undercounted silently.
